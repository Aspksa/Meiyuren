# Meiyuren v0.6: диагностика Cloud.ru, SSE и SQLite

## Диагностика

`GET /api/cloud/diagnostics` проверяет наличие ключа, доступность `GET /v1/models`, наличие выбранного ID в списке и примерную задержку. Этот вызов **не запускает генерацию и не подтверждает, что модель примет конкретный запрос**.

Тестовый вызов выполняется отдельно после подтверждения пользователя. Это обычное сообщение в основном диалоге, и **он может быть платным**. API-ключ не возвращается из backend.

## Потоковые ответы

`POST /api/chat/stream` принимает JSON `{text,requestId,conversationId}`. Браузер подключается по `fetch` и обрабатывает события SSE `delta`, `done`, `error`. Backend передаёт `stream: true` в Cloud.ru, буферизация отключена.

`done` означает, что ответ уже записан в SQLite. При отмене/обрыве поток маркируется как **неизвестный результат**, ответ и запрос могут не появиться в истории. Cloud.ru всё равно мог вычислить токены или завершить генерацию. Повтор с тем же ID заблокирован; новый запрос требует предупреждения о стоимости. Сервер не способен гарантировать отмену уже выполняемой генерации у провайдера.

## Диалоги и память

- Основной диалог `main` сохраняет историю прежних версий; дополнительные диалоги создаются с UUID.
- Таблица `memory_facts`: только факты, сохранённые пользователем самостоятельно; не происходит автоматического извлечения из переписки.
- Поиск использует параметризованный SQLite LIKE, работает по локальной истории. Экспорт и синхронизация пока отсутствуют.
- Данные сохраняются в `data/meiyuren.sqlite3` рядом с приложением, не отправляются в Cloud.ru кроме контекста при включённом облаке.

## Тестирование

Тесты мокируют Cloud.ru, не отправляют реальные данные и не создают расходов. Windows CI использует CMD, Linux — Bash. Режим Cloud.ru требует ключ, сохранённый локально в системном хранилище.

## Защита от сбоев потока (последующие исправления)

- Cloud.ru: тайм-аут соединения 12 с, отсутствия входящих данных 60 с, общая длительность потока не более 180 с; явные ограничения числа и размера SSE-событий.
- `[DONE]` обязателен для фиксации ответа в SQLite, пустые и пробельные ответы отклоняются. Ответ за пределами локального лимита не считается успешно завершённым.
- Некорректные `delta`, `choices`, повреждённый JSON, событие `error` и неожиданный EOF обрабатываются как ошибки; исходное тело ошибки провайдера не выдаётся в интерфейс.
- Нового платного запроса **автоматически не происходит**. Механизм сохранения идентификаторов и блокирования неопределённых результатов остаётся прежним. Остановка потока и тайм-аут не гарантируют отмены начислений на стороне провайдера.

## Проверка совместимости модели без генерации

Настройки Cloud.ru обращаются к `GET /api/cloud/compatibility?model=...` после выбора модели. Сервер использует только `GET /v1/models`: анализирует тип модели, явное `supports_streaming`, `supported_parameters` и `max_model_len`, если эти поля фактически представлены в ответе.

**Три состояния**: `compatible` — все проверяемые поля явно подтверждают параметры; `incompatible` — обнаружено явное противоречие; `unknown` — метаданных недостаточно. В реальном ответе Cloud.ru поля, описывающие поддерживаемые параметры, могут отсутствовать, поэтому статус «неизвестно» нормален. Это **не обещание, что конкретный запрос заработает**: совместимость может зависеть от токенизации и конкретной модели.

Проверка не делает платных запросов чата, а кнопка «Тест ответа (платно)» остаётся отдельной, с подтверждением. Некоторые модели ожидают `max_completion_tokens` вместо текущего `max_tokens`; если сервер явно сообщает это в `supported_parameters`, интерфейс блокирует применение конфигурации.

Модуль не выполняет автоматические повторные попытки, в том числе в случае `429` и временных ошибок сети.
